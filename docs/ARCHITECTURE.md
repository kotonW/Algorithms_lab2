уточнена по ходу реализации: цель — `net10.0`, только растровый рендер, добавлена вторая
задача (ханойские башни), экспорт в PNG не делался.

Версии заданы в `Directory.Packages.props` (Central Package Management), целевая
платформа — в `Directory.Build.props`.

| Runtime | `net10.0` | — |
| UI | `Avalonia`, `Avalonia.Desktop`, `Avalonia.Themes.Fluent` | 11.3.22 |

поддерживает `net10.0`.

Правило зависимостей: `Domain` не зависит ни от чего, `Application` — только от `Domain`,
`Rendering` — от обоих, `App` — от всех. ScottPlot и SkiaSharp встречаются только в
`Rendering`, Avalonia — только в `App` (и в `Rendering`, потому что адаптер держит `AvaPlot`).

## 4. Доменная модель

### 4.1. Ковёр Серпинского

```csharp
Fill(x, y, size, level):
    if level == 0 или size <= 1:  закрасить квадрат; return
    child = size / 3
    для 9 частей, кроме центральной: Fill(...)
```

Ключевое отличие от «наивной» реализации: рекурсия не спускается до уровня 0, если часть
уже стала размером с пиксель. Это делает стоимость `O(число пикселей)`, а не `O(8^n)`.
Благодаря этому глубина 8 строится за ~110 мс при растре 2187².

Характеристики (используются в UI и в тестах):

| Величина | Формула |
|----------|---------|
| Число клеток | `8^n` |
| Площадь фрактала | `(8/9)^n` |
| Площадь «дыр» | `1 − (8/9)^n` |
| Фрактальная размерность | `log 8 / log 3 ≈ 1,8928` |

> При проектировании в первой версии документа площадь была записана как `1 − (8/9)^n` —
> это площадь вырезанных дыр, а не самого фрактала. Ошибку поймал тест, сравнивший
> теоретическую долю с фактической долей закрашенных пикселей.

### 4.2. Ханойские башни

`HanoiSolver` умеет строить список ходов двумя способами: рекурсией (`Solve`) и явным стеком
(`SolveWithStack`), результаты обязаны совпадать ход в ход — это проверяется тестом и кнопкой
сравнения в интерфейсе. `HanoiPuzzle` хранит состояние стержней (снизу вверх), умеет шагать
вперёд, назад и переходить к любому ходу; индекс за пределами диапазона прижимается к нему,
поэтому «шаг назад» в самом начале просто ничего не делает.

## 5. Рендеринг

### 5.1. Почему растровый режим

Наивная отрисовка полигонами даёт `8^n` объектов: 262 144 при глубине 6 и 16,7 млн при 8.
Граф плюмбалов в ScottPlot перерисовывается на каждый кадр, поэтому пан и зум превратились
бы в слайд-шоу. Вместо этого:

1. Домен строит `GrayRaster` — `byte[]` с 0/255, без зависимостей от графики.
2. `RasterImageFactory` переводит его в `byte[высота, ширина, 3]` с цветами палитры.
3. `SierpinskiPlotRenderer` создаёт `ScottPlot.Image` и один плюмбал `ImageRect`.
4. В графе всегда **один** объект, независимо от глубины.

Разрешение растра отвязано от глубины: `RenderLimits.PixelSideFor` даёт `3^depth`, но не
меньше 243 и не больше 2187 пикселей (2187² ≈ 4,8 МБ). Восьмой уровень при таком растре
мельче пикселя, поэтому максимальная глубина ограничена семью: `3^7 = 2187` — ровно сторона
растра, и теоретическая площадь совпадает с фактической долей пикселей.

### 5.2. Пропорции

`ImageRect` растягивается на прямоугольник `(0,0)–(1,1)`, а окно не квадратное. Чтобы
фрактал не искажался, рендерер получает соотношение сторон области рисования и расширяет
диапазон по более «длинной» оси. То же сделано для башен: кольца сохраняют пропорции, а
поля добавляются слева и справа (или сверху и снизу).

Соотношение сторон берётся из `AvaPlot.Bounds` в `AvaPlotCanvas`, а при изменении размера
окна контрол перерисовывается (подписка на `SizeChanged` в code-behind View).

### 5.3. Ханойские башни

Каждый кадр строится с нуля: основание, 3 стержня-линии, кольца и подписи A/B/C. Элементов
мало (максимум ~25 при 10 кольцах), поэтому пересборка дешевле, чем обновление существующих
плюмбалов на месте.

Размеры сцены фиксированы: высота стержня, положение стержней и плита основания не зависят
от числа колец. При увеличении количества колец уменьшается только их толщина
(`usableHeight / diskCount`), поэтому масштаб картинки не «прыгает».

Кольца рисуются не прямоугольниками, а полигонами со скруглёнными углами
(`DrawRoundedRectangle` в `HanoiPlotRenderer`): у прямоугольников слишком грубый вид.
Цвет — градиент от светло-голубого (маленькое кольцо) к насыщенному синему (большое),
плюс затемнённая обводка для чёткости на тёмном фоне.

## 6. Поток данных

### 6.1. Ковёр

```
Ползунок глубины → SierpinskiSettingsViewModel.Depth
   → событие SettingsChanged
   → SierpinskiPlotViewModel.RefreshAsync()
       отменяет предыдущий запрос (CancellationTokenSource)
       пауза 90 мс (сглаживание перетаскивания)
       Task.Run → FractalRenderer.Render
       возврат в UI-поток → IFractalCanvas.Show(raster, palette)
       обновление статистики в правой панели
```

Важно: `Plot` в ScottPlot не потокобезопасен, поэтому все обращения к нему идут из UI-потока.
Сама растеризация — в фоне.

### 6.2. Пошаговая отрисовка (F10)

Если включён флажок, вместо одного кадра показываются кадры для глубин `0..n` с паузой
180 мс. Это те же данные, что и в обычном режиме, просто «проявленные» по шагам.

### 6.3. Башни

```
Кнопка/таймер → HanoiSettingsViewModel → HanoiSession.Step()
   → событие Changed(snapshot)
   → HanoiPlotViewModel → IHanoiCanvas.Show(snapshot)
   → HanoiSettingsViewModel обновляет счётчики
```

`HanoiSession` — общий объект для обеих ViewModel, поэтому визуализация и счётчики всегда
согласованы.

## 7. Интерфейс

`MainWindow` — сетка из трёх колонок (250 / `*` / 370). Левая колонка — `ListBox` задач,
центр и право — `ContentControl`, содержимое которых подставляется через `DataTemplate`
из `App.axaml`:

| ViewModel | View |
|-----------|------|
| `SierpinskiPlotViewModel` | `SierpinskiPlotView` (AvaPlot) |
| `SierpinskiSettingsViewModel` | `SierpinskiSettingsView` |
| `HanoiPlotViewModel` | `HanoiPlotView` (AvaPlot) |
| `HanoiSettingsViewModel` | `HanoiSettingsView` |

Связь View ↔ ViewModel односторонняя, кроме одного места: View создаёт `AvaPlotCanvas`
поверх своего `AvaPlot` и передаёт его в ViewModel через `Attach`. Так ViewModel не знает
про ScottPlot и остаётся тестируемой.

Тема оформления — `ThemeVariant` приложения; кисти панелей описаны в
`ResourceDictionary.ThemeDictionaries` с отдельными наборами для светлой и тёмной темы.

Графики ScottPlot тему сами не подхватывают (по умолчанию у них белый фон), поэтому:

- `AppTheme` хранит текущий режим, `ThemeService` обновляет его вместе с `ThemeVariant`;
- `AvaPlotCanvas` при создании сразу красит фон и оси — иначе до первого кадра видна
  белая плоскость;
- при переключении темы `MainWindowViewModel` обходит задачи, реализующие
  `IRedrawableTask`, и просит их перерисоваться; у графика замеров с пустыми данными
  вызывается `RefreshTheme` — перекрашиваются только оси и фон.

Панорамирование и зум на графике замеров остаются штатными средствами ScottPlot;
клик по точке обрабатывается отдельно и отличается от перетаскивания по порогу
смещения мыши (4 DIP).

## 8. Ограничения

| Что | Значение | Почему |
|-----|----------|--------|
| Глубина фрактала | 0–7 | `3^7 = 2187` совпадает со стороной растра, глубже уровень мельче пикселя |
| Сторона растра | 243–2187 px | 2187² ≈ 4,8 МБ, компромисс память/качество |
| Колец в башнях | 1–10 | 2^10 − 1 = 1023 хода, проигрывание остаётся осмысленным |
| Задержка между ходами | 20–600 мс |  |
| n для замеров перестановок | 1–15 | 15! ≈ 1,3 трлн операций: это часы, поэтому в UI есть оценка времени и отмена |

## 9. Тесты

109 тестов (xunit v3), запускаются как обычный исполняемый файл:

- `FractalMathTests` — формулы `8^n`, `(8/9)^n`, размерность.
- `SierpinskiCarpetTests` — число клеток, границы, отсутствие пересечений, совпадение
  фактической доли закрашенных пикселей с теорией, детерминизм, валидация аргументов.
- `HanoiSolverTests` — рекурсия и стек дают одинаковую последовательность ходов, её
  легальность и минимальность.
- `HanoiSessionTests` — «шаг назад» в начале ничего не делает и не роняет приложение,
  откат и переход к произвольному ходу, смена числа колец.
- `HanoiPuzzleTests` — минимальное число ходов, легальность каждого хода, финальное
  состояние, шаг назад, счётчики.
- `PermutationGeneratorTests` — `n!` для известных значений, ровно `n!` различных
  перестановок, каждая является перестановкой `1..n`, валидация аргументов.
- `PermutationsBenchmarkTests` — метаданные алгоритма, совпадение `RunOnce` с `n!`,
  выход за диапазон n, реестр алгоритмов.
- `BenchmarkRunnerTests` — по точке на каждое n, число прогонов на точку, прогресс,
  отмена, границы среднего, разбор конфигурации эксперимента.
- `RenderLimitsTests` — границы глубины и разрешения, согласованность статистики с растром.
- `JsonSettingsStoreTests` — сохранение/чтение/битый файл/создание каталога.

## 10. Подсистема замеров (как добавить новый алгоритм)

Идея взята из первой лабораторной и перенесена на интерфейсы нашего приложения:

| Слой | Тип | Роль |
|------|-----|------|
| Domain | `ITimedAlgorithm<TInput, TResult>` | чистый алгоритм: `Execute(input)`, без замеров |
| Application | `IAlgorithmBenchmark` / `AlgorithmBenchmark` | описание алгоритма + `RunOnce(n)` |
| Application | `TimedAlgorithmBenchmark<TInput, TResult>` | адаптер «любой алгоритм → бенчмарк» |
| Application | `ExperimentConfig` | `MaxN`, шаг, число прогонов на точку |
| Application | `BenchmarkRunner` | Stopwatch, R прогонов на точку, среднее/минимум/максимум |
| Application | `BenchmarkRegistry` | список алгоритмов, наполняется через DI |
| Rendering | `BenchmarkPlotRenderer` | график измерений + теоретическая кривая `c·f(n)` |
| App | `BenchmarkSettingsViewModel` | параметры, запуск, таблица точек |
| App | `BenchmarkChartViewModel` | холст графика, выбор точки по клику |

Добавление нового алгоритма сводится к двум шагам:

```csharp
// 1. Алгоритм: чистый класс без знания о UI и замерах.
public sealed class MyAlgorithm : ITimedAlgorithm<int, long>
{
    public string Name => "Мой алгоритм";
    public long Execute(int n) => /* ... */;
}

// 2. Регистрация: одна строка в ServiceConfiguration.
services.AddSingleton<IAlgorithmBenchmark>(sp =>
    new TimedAlgorithmBenchmark<int, long>(
        new MyAlgorithm(),
        myMetadata,          // имя, сложность, описание, диапазон n
        n => n));            // как из n получить вход алгоритма
```

После этого алгоритм сам появляется в выпадающем списке раздела «Замеры», и для него
можно построить график — ни одного нового View или ViewModel писать не нужно.

Коэффициент `c` теоретической кривой подбирается методом наименьших квадратов:
`c = Σ(yᵢ·fᵢ) / Σ(fᵢ²)`. Если измерения лежат на кривой `n!`, линии почти совпадают —
это и есть визуальное подтверждение оценки `O(n!)`.

## 11. Возможные расширения

- Новые фракталы: реализовать `IFractal` и добавить пункт в список задач.
- Новые замеряемые алгоритмы: реализовать `ITimedAlgorithm` и зарегистрировать бенчмарк.
- Экспорт графика в PNG: `IPlotExporter` над `Plot.SavePng`.
- Тайлинг растра для глубин ≥ 9.
